# M4.5 — Change Impact Engine

## Objective

Answer a question that becomes critical in long-running fiction projects:

"When this Canon fact, name, alias or relationship changes, what else should be reviewed?"

M4.5 materializes project dependencies, creates invalidation events when important world data changes, previews transitive impact, and selectively reruns M4 Lint only on affected manuscripts.

## Design-review meeting

### Socratic review

A change is not automatically an error. The system must distinguish "this changed" from "all dependent text is wrong."

Result: M4.5 produces impact candidates and invalidation records. The author chooses revalidation or dismissal; downstream prose is never rewritten automatically.

### Strategy review

The valuable product capability is not just detecting inconsistencies after the fact. It is knowing which pieces of a large story depend on a changed fact.

Result: M4.5 links Bible entities to aliases, manuscript references, timeline events and relation edges, then reuses that graph to target later verification.

### Systems review

Re-running every rule across an entire multi-volume project after every Canon edit wastes time and compute.

Result: Bible/Canon/Alias/Relation changes enqueue invalidations. Selective revalidation follows dependency edges and runs M4 document lint only for affected manuscripts.

### Guest — build-system / incremental-computation engineer

A dependency system should be rebuildable from source state, bounded during traversal, explainable edge-by-edge, and safe when cached indexes are missing.

Result: the dependency graph is materialized but replaceable, traversal has a configurable bounded depth, every edge carries type/detail metadata, and surface-reference fallback can find obvious manuscript dependencies even before Entity Mention indexing has run.

## Dependency graph

Current materialized edge families include:

### Alias dependencies

BibleEntity → EntityAlias

edge type: has_alias

### Mention dependencies

BibleEntity → EntityMention

edge types:
- resolved_mention
- candidate_mention

EntityMention → ManuscriptDocument

edge type:
- appears_in

### Direct surface references

BibleEntity → ManuscriptDocument

edge type:
- surface_reference

The fallback checks canonical names and aliases against normalized manuscript text. It records whether the matching surface came from a canonical name or alias and the manuscript revision inspected.

This is an impact-discovery fallback, not a replacement for M3.5 span-level Entity Mention resolution.

### Timeline dependencies

BibleEntity → TimelineEvent

edge type:
- participates_in

### Relation dependencies

BibleEntity → EntityRelation

edge types:
- relation_source
- relation_target

EntityRelation → BibleEntity

edge type:
- relation_endpoint

This lets impact traversal reach another entity through a stored relationship and continue into that entity's dependent material.

## Impact preview

The engine performs bounded breadth-first traversal from a Bible entity.

Current configurable traversal depth is 1–6, with 4 as the normal UI path.

The result explains:

- affected manuscript ids
- affected timeline event ids
- related entity ids
- every traversed node
- every traversed edge
- depth and edge details

The author can inspect the path rather than receiving a black-box "this chapter may be affected" claim.

## Invalidation queue

Important project mutations create PENDING invalidations.

Currently integrated mutation sources include:

- Story Bible entity updates
- Canon-state transitions
- alias additions
- relation creation, for both endpoints

Each invalidation records source type/id, change kind, detail and lifecycle state.

States:

- PENDING
- REVALIDATED
- DISMISSED

## Selective revalidation

For a PENDING BibleEntity invalidation:

1. rebuild the dependency graph from current source state,
2. calculate impact,
3. collect affected manuscripts,
4. run M4 document lint only on those manuscripts,
5. store the resulting lint run ids and impact summary,
6. mark the invalidation REVALIDATED.

This creates the first incremental-verification loop in Creative Consistency OS.

## Author dismissal

A user may decide that a change has no practical downstream risk.

Dismissal requires an explicit reason in the API and marks the invalidation DISMISSED. It does not alter dependent content.

## Serialization hardening

M4.5 change details can contain timestamps from domain records. During CI, an invalidation containing datetime values exposed a JSON serialization failure.

The repository layer now serializes impact detail/result payloads safely while retaining the original structured content as strings where necessary.

This failure was found by integration testing rather than hidden behind an API catch.

## Planning additions

No new top-level milestone is required.

The implementation establishes two rules for subsequent work:

- M5–M7 rules must declare what dependency types can invalidate their results.
- M8 AI Co-Author must consume the same dependency/Canon model and must never treat a stale or unresolved dependency as silently confirmed context.

At Closed Beta, dependency fan-out and graph size should be measured on real long-running manuscripts before introducing retention/compaction or more complex graph partitioning.
