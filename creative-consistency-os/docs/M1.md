# M1 — Application Foundation

## Objective
Turn the M0 architecture into a runnable local-first foundation without prematurely implementing World Builder or full Lint behavior.

## Sub-milestones
- M1.1 Repository bootstrap and runtime boundaries
- M1.2 FastAPI application and configuration
- M1.3 SQLite persistence, repository layer, migration baseline
- M1.4 Next.js application shell and Golden Path entry screens
- M1.5 ChangeLog and schema-version primitives
- M1.6 Health diagnostics, tests, and CI
- M1.7 Developer experience and recovery baseline

M1.6 and M1.7 were added during review as sub-milestones; they improve operational quality without changing top-level product scope.

## Meeting outcome

### Socratic review
Author-confirmed facts and machine inference must remain distinct. M1 defines canon-state and source primitives now so later AI work inherits the boundary.

### Strategy review
Durable project knowledge is the product moat. Persistence and repository boundaries therefore precede AI generation.

### Systems review
SQLite is local-first storage. Service/domain code remains insulated from SQLAlchemy so a PostgreSQL implementation can be introduced later.

### Guest — software architect / QA
Health diagnostics, migration verification, tests and CI belong in the foundation, not in later polish.

## Architecture decisions
1. Modular monolith first.
2. Local-first; cloud is not mandatory.
3. SQLite now, PostgreSQL-capable repository boundary later.
4. AI inference never becomes Canon implicitly.
5. Schema migrations are mandatory.
6. Change history begins before World Builder.
7. Health/tests/CI are M1 foundation work.

## Deferred
World Builder, Language DNA, Entity Linking, Lint evaluation, manuscript autosave, cloud sync, authentication and collaboration.
