# M6 — LN Genre Packs

## Objective

Add three independent, combinable light-novel genre packs on top of the M4 diagnostic contract and M4.5 change-impact system:

- Noble Lady / aristocratic society
- Palace / harem / court
- Romantic Comedy

M6 deliberately does not introduce a mandatory primary genre. A project may enable none, one, two or all three packs.

## Design-review meeting

### Socratic review

A genre trope is not a law.

A heroine may intentionally break etiquette. A court character may trespass. A romance may jump several stages after a major event. Therefore the system must distinguish structured inconsistency from authorial intent.

Result:

- all three packs are opt-in,
- every M6 result is an M4 Finding,
- findings never rewrite prose or Canon,
- the author can acknowledge, ignore or resolve findings,
- no pack receives hidden priority when several packs are enabled.

### Strategy review

A generic "AI says this feels wrong" feature is difficult to audit and easy to imitate.

The stronger product layer is a reusable social-state model:

status hierarchy → relationships → permissions → events → violations → evidence → impact.

Result:

M6 works from Story Bible attributes and Entity Relations. The same structured facts can later feed AI Co-Author context, exports and cross-media/game logic.

### Systems review

Long serials cannot afford a full semantic LLM pass every time a title, faction or relationship changes.

Result:

M6 deterministic checks run in a new structural-lint scope. M4.5 now performs structural revalidation after BibleEntity changes in addition to re-linting only affected manuscripts.

This preserves the incremental design while ensuring a setting-only contradiction is not missed.

### Guest — light-novel editor / continuity editor

The three packs have different failure modes:

- Noble Lady: rank, house, title, engagement and forms of address.
- Palace/Harem: rank, faction, restricted space, information access and ritual order.
- Romantic Comedy: relationship progression, impossible schedules and misunderstandings that are resolved before they exist or silently disappear.

Result:

M6 keeps one common diagnostic interface but separate state contracts and rule families.

## Pack independence

Stored configuration:

enabled_packs:
- noble_lady
- palace_harem
- romcom

Each is a boolean.

This is intentionally independent of World Builder genre selection. Selecting a genre may be used later for recommendations, but does not silently enable a pack.

character.attributes.ln_noble:

- house_entity_id
- rank

### Address-event contract

### Engagement graph

### Configurable policy

## Structural Lint

M6 adds a dedicated M4-compatible run scope:

structure

Unlike project lint, structural lint does not rescan every manuscript. It runs project/Bible/relationship checks only.

This is important for incremental revalidation. A change to a noble house or court rank can alter setting consistency even when no manuscript text has changed.

API:

POST /projects/{project_id}/lint/run-structure

The result is stored in the same lint_runs / lint_findings system and therefore retains:

- rule id
- category
- severity
- entity reference
- evidence
- fingerprint
- finding lifecycle

## M4.5 integration

Saving M6 policy creates:

source_type = LNGenrePackConfig
change_kind = LN_GENRE_PACK_CONFIG_UPDATED

A pack-policy change can affect the whole project, so its revalidation performs project lint.

A normal BibleEntity change remains dependency-driven:

1. rebuild the dependency graph,
2. find affected manuscripts,
3. re-lint those manuscripts,
4. run one structural lint pass,
5. store all resulting run ids in the invalidation result.

This fixes an important gap discovered during M6 review: document-only selective revalidation could miss structured setting contradictions.

## M6 structured dependency edges

M4.5 now derives additional edges from Story Bible attributes:

- noble_house_member
- palace_faction_member
- palace_access_actor
- palace_access_place
- palace_information_actor
- romcom_transition_source
- romcom_transition_target
- romcom_schedule_participant

Example:

House BibleEntity
→ noble_house_member
→ Character BibleEntity
→ surface_reference
→ ManuscriptDocument

Changing a house can therefore reveal chapters containing its members even when the house name itself is not written in those chapters.

## Planning consequences

No M6.5 top-level milestone is required.

M7 should reuse the newly established concept of a structured ledger:

- Mystery: Evidence Ledger, Alibi/Timeline Ledger, Character Knowledge State.
- SF: Assumption Ledger, unit/order-of-magnitude checks, causality/relativity constraints, and an explicit hardness setting.

The deterministic ledger should remain separate from later AI advisory analysis. This distinction should be preserved through M8 AI Co-Author.
