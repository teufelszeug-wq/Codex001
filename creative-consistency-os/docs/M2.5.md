# M2.5 — Language & Culture Builder

## Objective

Turn the Language and Culture placeholders created in M2 into a real author-controlled subsystem that can support naming, scripts, language contact, etymology, culture-specific terminology, and later continuity linting.

The subsystem must allow both presets and fully custom construction. Real-world language references are inspiration inputs, not claims that the generated fictional language is authentic to that language.

## Design-review meeting

### Socratic review
A menu of presets is not true author choice. The author must be able to choose one inspiration, mix several, enter an arbitrary inspiration, use no real-world inspiration at all, or leave a common language undefined.

Result: M2.5 uses weighted inspiration entries and free-form custom sources. Common language is optional.

### Strategy review
A simple "Nordic name generator" is easy to copy. Durable value comes from keeping a causal chain across phonology, naming, script, language lineage, cultural use, loanwords, roots, reader-facing rendering, and later Lint.

Result: language data is stored as a persistent project subsystem, not as disposable prompt text.

### Systems review
Language and culture configuration can grow combinatorially. M2.5 therefore keeps stable language/culture/root IDs inside a flexible project-level configuration while enforcing cross-reference validation. A later milestone may normalize high-volume entities without breaking this contract.

Result: references between cultures, languages, contacts and roots are validated before persistence.

### Guest — constructed-language / historical-linguistics specialist
Plausible naming is not just phoneme replacement. Useful minimum structure is phonotactics + naming morphology + script metadata + language contact + lexical roots + lineage. Cultural borrowing also needs to distinguish native words, adapted loans and calques.

Result: a deterministic name-preview engine, lineage field, root lexicon and directional language-contact model were added.

## Implemented model

Each project can hold multiple fictional languages and cultures.

A language records:
- stable id
- name and role
- regions
- weighted inspirations
- optional parent language and era label
- onset/nucleus/coda pools
- forbidden sequences
- syllable range
- naming prefixes/suffixes by person/place/item/title
- script name/type/direction
- notes

A culture records:
- stable id
- regions
- linked language ids
- free cultural tags
- institutions
- etiquette
- taboos
- festivals
- material culture
- notes

Cross-language contact records:
- source language
- target language
- intensity
- domains such as trade/religion/migration/scholarship
- borrowing policy
- notes

Root lexicon records:
- root id
- language id
- form
- meaning
- semantic tags
- origin classification
- notes

## Inspiration handling

Built-in inspiration entries include broad modern/family styles and special historical/cultural inspirations, but the catalog is not exhaustive.

The current catalog includes optional entries such as Nordic-like, Japanese-like, Sinitic-like, Indic-like, Ainu-inspired, Old-Japanese-inspired, speculative Jomon imagery, and Katakamuna visual inspiration.

The latter categories are deliberately labeled as inspiration modes. The system does not present speculative reconstruction or symbolic inspiration as verified historical language.

## Reader-facing translation layer

M2.5 separates in-world language from what the reader sees.

Projects can configure:
- translated display
- original + reading
- mixed rendering
- custom rendering
- first-mention policy
- later-mention policy
- ruby policy

This prevents the internal language model from forcing one publication style.

## Earth-Origin terminology foundation

M2.5 does not yet ship the large detection dictionary. It creates the persistent policy consumed later by the Isekai pack:

- OFF / WARN / STRICT
- descriptive replacement
- world-origin replacement
- both
- custom
- context exceptions

The actual manuscript detector and broad term database remain M5 work.

## Name preview engine

A deterministic server-side preview generator is implemented for:
- person names
- place names
- item names
- titles

It uses the saved phonology and naming rules. A fixed seed produces reproducible previews, which makes author review and testing possible.

The preview generator is a design aid. Generated names are not automatically Canon.
