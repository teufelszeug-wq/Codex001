# M4 — Core Lint Engine

## Objective

Turn the data created by World Builder, Story Bible, Writing Room and Entity Intelligence into an author-controlled consistency inspection system.

M4 is not an auto-rewriter. It produces diagnostics with evidence, severity and lifecycle state. The author decides whether a finding is relevant, acknowledged, ignored, resolved, or should lead to a Canon/manuscript change.

## Design-review meeting

### Socratic review

An inconsistency signal is not the same thing as truth. A draft may intentionally contradict Canon, an unreliable narrator may use the wrong name, and an unresolved term may be deliberate.

Result: Lint never mutates manuscript text or Canon automatically. Findings are persisted as evidence-backed diagnostics. The author can triage them independently of the manuscript.

### Strategy review

Spelling and grammar checking alone are commodity capabilities. The defensible layer is project-specific consistency checking over Canon states, entity resolution, aliases, timeline and relationship structure.

Result: Core Lint consumes the project's own structured data and exposes a stable extension point for M5–M7 genre packs.

### Systems review

Running expensive semantic inference on every keystroke would scale poorly and create non-reproducible output.

Result: M4 begins with deterministic and structured-semantic rules, explicit project/document runs, stable rule ids and deterministic fingerprints. Later AI-semantic providers must preserve evidence and author control instead of replacing this layer.

### Guest — static-analysis / compiler engineer

A useful diagnostic system needs stable rule ids, severity, source spans, reproducible evidence, suppression/triage and stale-analysis detection.

Result: M4 stores lint runs and findings, detects stale Entity Mention indexes, checks mention-span integrity, supports custom project constraints, and keeps a durable finding lifecycle.

## Severity model

M4 uses four author-facing severity levels:

- HINT — weak suggestion or stylistic/lexical possibility
- INFO — noteworthy state that may be intentional
- WARNING — probable consistency issue requiring review
- ERROR — strong integrity/Canon problem

Severity is policy, not truth. Every built-in rule can be disabled or have its severity changed by the project.

### Mention freshness

Entity Mention records are bound to a manuscript revision. If the manuscript advances without a rescan, the old mention index is treated as stale rather than current evidence.

### Mention span integrity

Even when a stored mention claims the current revision number, its text span is checked against the actual manuscript slice. A mismatch is an ERROR and requests a rescan.

### Canon-state reference checks

Resolved mentions can warn when prose references entities still in INFERENCE, DISPUTED, DEPRECATED, ARCHIVED or REJECTED states.

This does not forbid the author from doing so. It makes the state visible.

### Lexical drift hint

An unresolved surface form is compared with known canonical names and aliases using deterministic lexical similarity. High-similarity candidates are presented as HINT findings with the similarity score and provider id in evidence.

This is deliberately a suggestion layer, not automatic entity resolution.

## Project structural checks

Project-level lint also checks:

- duplicate normalized canonical names
- aliases shared by multiple entities
- CANON timeline events referring to non-CANON participants
- CANON entity relations whose endpoints are not CANON

These rules operate on structured project state rather than prose interpretation.

## Custom constraints

Projects can define literal term rules with:

- stable id
- term
- enabled flag
- severity
- case-sensitivity
- custom message

This is the extension substrate that the M5 Earth-Origin Guard can build on, though M5 will add richer origin/category/context semantics rather than remaining a plain forbidden-word list.

## Persistence

M4 adds:

- lint_project_configs
- lint_runs
- lint_findings

Migration: 0006_core_lint_engine

A Lint Finding stores rule id, category, severity, message, document/entity references, source offsets, evidence JSON, deterministic fingerprint and lifecycle state.

Finding lifecycle:

OPEN → ACKNOWLEDGED / IGNORED / RESOLVED

A finding state change does not change the manuscript or Canon.

## Downstream contract

M5–M7 genre packs should register or compose rules through this diagnostic contract rather than building isolated warning systems.

Future AI-semantic rules must:
1. preserve evidence/provenance,
2. report uncertainty,
3. never auto-rewrite Canon or prose,
4. remain project-configurable.
