# M3.5 — Entity Intelligence

## Objective

Make Story Bible entities usable inside real prose. M3.5 adds aliases, manuscript mentions, explicit ambiguity, deterministic reference resolution, author-controlled candidate promotion, and an entity relation graph.

This milestone is the bridge between Writing Room and M4 Lint.

## Design-review meeting

### Socratic review

The same surface word can legitimately refer to more than one entity. Guessing one answer would turn uncertainty into false Canon.

Result: ambiguity is a first-class resolver state. The system returns all candidates and waits for author resolution instead of silently choosing one.

### Strategy review

The product moat is not generic named-entity extraction. It is a persistent mention graph that connects prose spans to the author's canonical world model and can later drive Lint and impact analysis.

Result: mentions persist document id, revision number, text offsets, confidence, candidate ids and resolution state. Relations are also stored as graph edges.

### Systems review

Calling an LLM/NER pipeline on every keystroke is costly, slow and difficult to reproduce.

Result: M3.5 uses deterministic canonical-name and alias matching first. Candidate extraction is an explicit scan, not continuous AI inference. Low-confidence heuristics are clearly marked rather than promoted automatically.

### Guest — information-retrieval / entity-resolution engineer

Entity resolution needs normalization, reproducible spans, collision handling, longest-match behavior and manual override.

Result: reference keys use Unicode NFKC normalization + case folding; exact aliases can collide across entities; collisions produce AMBIGUOUS; mention spans are bound to a manuscript revision; longest overlapping matches win.

## Aliases

Aliases are attached to a stable Bible entity and can be classified as:

- alternate
- nickname
- title
- former_name
- translation
- epithet
- abbreviation
- other

The same normalized alias may belong to multiple different entities. This is intentional: reference resolution then reports ambiguity.

## Resolver

Normalization currently applies:

1. Unicode NFKC normalization
2. case folding
3. outer whitespace trimming
4. repeated whitespace collapse

Direct resolution states:
- RESOLVED — exactly one entity matches
- AMBIGUOUS — multiple entities match
- UNRESOLVED — no known entity matches

The resolver does not turn ambiguity into a guessed answer.

## Manuscript mention scan

Known canonical names and aliases are matched deterministically.

When candidate extraction is enabled, the current heuristic layer can surface:
- terms inside 《...》
- longer Katakana sequences
- capitalized Latin-script proper-name candidates

These heuristics are deliberately low-confidence. They are discovery aids, not Canon assertions.

Mentions record:
- document id
- manuscript revision number
- source span offsets
- surface text
- normalized text
- linked entity when resolved
- resolver state
- confidence
- candidate ids
- resolution note

## Candidate promotion

An unresolved manuscript mention can be converted into a Story Bible entry only through an explicit author action.

The resulting entity is:
- Canon state: INFERENCE
- source type: MANUSCRIPT
- source reference: document + text span

It still requires the normal M3 Canon-promotion workflow before becoming CANON.

## Relation graph

M3.5 also stores directed entity relations. Initial relation vocabulary includes family, friend, rival, enemy, romance, member_of, serves, owns, located_in, created_by, uses, knows, allied_with, opposes and custom.

Self-edges are rejected. Both endpoints must exist in the same project's Story Bible.

Relations are not implicitly CANON; the UI creates them as PLAN by default.
